# Known issues / not done (v0.1.0-alpha + steps 15-24)
**Read this first.** The older entries below (v2-v6, steps 16-17) describe the state *at that time*; later steps lifted many of those limits (Linux now has fork/exec, pipes, sockets, threads, dynamic linking, signals, timers; Windows has msvcrt, threads, DLLs, exceptions). The block right here is the **current** list; where an older entry contradicts it, this one wins. The authoritative step-by-step record is `docs/HANDOFF.md` section 9.
**Current limits (after step 24):**
* *Verification:* QEMU q35 (BIOS + UEFI/OVMF) only, on the distro's rustc 1.75; never on real hardware, never with more than 1 CPU; the pinned-nightly build path has not been run by the author.
* *Signals (Linux):* delivered asynchronously on timer ticks and at syscall exit; per-thread masks and `tkill/tgkill/pthread_kill`; one pending bit per signal (no queued payloads, no `sigqueue`/`rt_tgsigqueueinfo`); no SIGBUS/SIGTRAP/x87-SSE exception signals; `rcx`/`r11` are not preserved across handlers for *syscall- and fault-built* frames (they are for timer-interrupted code); futex waits, console reads, `nanosleep`, pipes and `accept/recv/wait4` are interruptible, `connect` is interruptible but untested.
* *Job control:* process groups, sessions, group `kill`/`wait4`, SIGSTOP/SIGTSTP/SIGCONT, `WUNTRACED/WCONTINUED`, Ctrl-C to the programs the shell started. No controlling-terminal semantics (`tcsetpgrp`, SIGTTIN/SIGTTOU, SIGHUP), no Ctrl-Z, no `jobs/fg/bg` in deloxy-sh, no ptrace, Linux processes only.
* *Windows exceptions:* vectored handlers, `SetUnhandledExceptionFilter`, `RaiseException`, hardware faults with a real CONTEXT/EXCEPTION_RECORD, and (step 25) **table-based SEH** through the user-mode runtime `deloxy_seh.dll`: `.pdata` unwinding, `RtlUnwindEx`, `__C_specific_handler` scope tables, mingw C++ `throw/catch` (statically linked libstdc++). Gaps: no epilogue detection, no unwind info v2, no `RtlAddFunctionTable`/JIT, no stack-overflow exceptions, no `#BP`/FP exceptions, clang/MSVC-built `__try` programs and dynamically linked `libstdc++-6.dll`/`libgcc_s_seh-1.dll` untested.
* *Files app:* browses folders, New folder, Delete; no rename/copy/move/drag-and-drop; wallpapers only from the top-level folder.
* *Test coverage gaps:* `connect` interruption, the partial-line restore on the *Windows* console path, real tty semantics. Programs stored on disk are not signature-checked.
* *Publishing:* the repository bundles prebuilt third-party test binaries in `user/blobs/` (Ubuntu glibc 2.39 and libstdc++/libgcc_s shared libraries, statically linked glibc/OpenSSL test programs, MinGW-built PE programs; see `NOTICE`; CPython and `file` are *not* in the repo, they only go into the optional full ISO built by `tools/mkfull-iso.sh`); `user/poc/tls/` holds throw-away TEST certificates/keys; the update key is a public TEST key. None of these are secrets, none are production credentials.
**Not verified:** storage on real media / power loss on real disks (QEMU + fault-injected RAM disk only); boot on real hardware (only QEMU q35, BIOS and UEFI/OVMF); the pinned-nightly toolchain path (all development used rustc 1.75 + workarounds); more than 1 CPU.
**Not implemented:** *activating* a staged update (staged updates are now saved to the store and re-verified at boot, but the kernel boots from the read-only boot medium); user-space sockets (only the in-kernel updater uses the network; `Net` capabilities exist but only `upd` consumes them);
DNS, TLS, IPv6, UDP/ICMP sockets for programs; real-NIC drivers (virtio-net only), real disk drivers (virtio-blk only: no NVMe/AHCI/USB), virtio interrupts/MSI-X; directories/partitions/fsck for the store; capability transfer over IPC; factory capability for client shm/channels;
SMP; SMAP; a real key ceremony (see SECURITY.md); a graphical monitor (the monitor is a text program); closing the terminal window.
**Rough edges:** program stdout (Linux/PE/native via the Tty cap) is a shared kernel stream: concurrent programs interleave. The terminal window renders ASCII only, 80x24, no scrollback, no ANSI.
The shell has no history, tab completion, pipes or job control (no Ctrl-Z/jobs/fg/bg); `run` waits for the program, and Ctrl-C ends a Linux program (step 24; PE/native programs are not interrupted). Process objects of killed processes may be kept alive by a blocked thread.
Linux layer: static single-threaded programs only; Win32 layer: freestanding kernel32-only programs (msvcrt imports fail with a named error).
Process ids grow quickly in the selftest because the loader fuzz creates thousands of processes; this is cosmetic.
**Store limits (v2):** hierarchical (dirs, symlinks, modes; no hard links, no owners), <= 20 000 inodes, <= 16 MiB per file, whole-file replace only (a commit rewrites the whole metadata image, so creating thousands of files one by one gets slower), `cp` in the shell <= 4 MiB between paths and <= 1 MiB between flat names, a v1-only kernel would roll a migrated disk back to its last v1 state, the Files app has no rename/copy/move; disk I/O is polled with interrupts off (timer ticks are lost while a large write runs); `upd.*` names are kernel-only; programs stored on disk are not signature-checked.
**Desktop (deloxy-de v2):** no resize/maximize, no keyboard shortcuts, one terminal only (closing it hides it), 8x16 font only, UTC clock without timezone, drag/animation not measured on real hardware; the compositor is still a kernel thread.
**Compat (deloxy-wltd v2):** Linux: single-threaded static programs only (no clone/fork/exec/pipes/sockets/getdents/signals/dynamic linking); Windows: only `kernel32` + `msvcrt` imports, bump-allocator `malloc` (free is a no-op), no qsort/atexit/scanf/wide stdio/C++ exceptions/threads/GUI, `%e`/`%g` print as `%f`, PE TLS callbacks ignored. Foreign files are flat names (initramfs read-only + store), whole-file buffered, <= 4 MiB.
**Desktop v3:** no window resize/maximize/snap, no right-click menus, no notifications, wallpaper formats: P6 PPM only, calendar is UTC, the Files app shows the first 11 rows per page (scroll with the buttons or arrow keys).
**Compat v3:** foreign stdin shares the one kernel TTY with the shell (don't type into two programs at once); `scanf` has no floating point; qsort is an O(n^2) in-place sort; file `mmap` is a private copy; `W` (wide) Win32 APIs are missing.
**Threads (v4)** [partly superseded: Linux signals and `tkill/tgkill` work since steps 17-22]: Windows waits poll every 1 ms; no condition variables/SRW locks/fibers; pipes cannot be dup2'd onto stdin/stdout; single CPU assumed for the atomicity of Interlocked/critical sections; `fork/exec` do not exist so shells/make/gcc-style programs cannot run.
**Permissions/limits (v5):** consent prompts appear on the terminal (not a DE dialog) and block the program's syscall until answered; grants are all-or-nothing; no accounts/login; 128 MiB cap is fixed (not configurable); native programs have no memory cap; kill_process assumes a single CPU.
**Sockets (v6):** TCP client only (no DNS/UDP/servers/TLS/IPv6), numeric addresses, every destination asked individually, consent in the terminal, one 10-minute 64 MiB grant per connection; Winsock lacks `select`/overlapped I/O; blocking `connect` waits up to 15 s.
**Full access:** an any-host rule also reaches your LAN unless set to internet-only; the time limit is wall-clock from the first connect of a run; there is no per-destination data accounting inside an any-host grant; no DNS/UDP/TLS yet.

**DLLs (step 16):** no thread attach/detach calls, no DLL TLS, no `DLL_PROCESS_DETACH` at process exit, dependencies stay loaded after their dependent is freed, freed DLL pages stay mapped until exit, a DLL is looked up by file name only (initramfs, then store root), no delay-load imports, no side-by-side manifests; concurrent `LoadLibrary` from two threads of one process can race on the shared init list.
**CPU-fault signals (step 17):** `#DE/#UD/#GP/#PF` only (no SIGBUS, SIGTRAP, x87/SSE exceptions), [superseded by the block at the top: Windows vectored exceptions exist since step 20, handled signals are asynchronous since step 19].
